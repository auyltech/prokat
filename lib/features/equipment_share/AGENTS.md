# Equipment share

- Ссылка: `Env.equipmentShareUrl(id)` → `https://<SHARE_BASE_URL>/e/<id>`. Хосты: `Env.shareTrustedHosts`.
- Исходящий шаринг: `?s=<shareId>`. `shareId` — 22 символа base64url без `=`, непрозрачный, новый на каждый акт шаринга (`generateShareId` сразу перед `SharePlus`).
- Analytics `share` и backend `SHARED` — только при `ShareResultStatus.success` (`reportShareResult`); `SHARED` только для авторизованного. Оба best-effort, независимы, не блокируют UI.
- `isShareableNow`: `AVAILABLE` + `isVisible` + есть цена `> 0`. Только тогда PNG и ссылка.
- `canShowShareButton`: `isModerated` (не draft / created / rejected / archived).
- `needsPublishAlert`: кнопка есть, но `isShareableNow` ложно. Алерт, Share не открывается.
- Кнопка: клиентская плитка, список собственника (не черновик, под бейджем статуса, круг `filled`), хедер фото собственника, экран брони. На деталях собственника перед шарингом `ownerEquipmentDetailsProvider.refresh()`.
- В PNG и тексте нет телефона, номера, GPS, `adminComment` и чужих id. Описание — `shortDescriptionOf`; пустое не рисуется.
- Картинка на устройстве: Overlay + `RepaintBoundary.toImage(pixelRatio: 1)`, файл 1080×1350. Не `Offstage`.
- Приём ссылки: `app_links` → `EquipmentShareIngress` → pending open → resolver для registry URL → durable overlay в `EquipmentShareStorage` → один `router.push('/e/<id>')` из consume bootstrap. Не `go`, не push из redirect. `afterAuth` после гостевого «Создать заказ». Выход через `clearForLogout` ревокирует pending, overlay, intent и accepted context до remote logout, но сохраняет consumed state install referrer. Flutter deep linking выключен.
- Registry ingress: только `https://open.prokat.auyltech.kz/e/<shareId>`; `prokat.auyltech.kz/e/<shareId>` всегда Web и не native ingress. Backend mobile resolver `/equipment-shares/resolve/<shareId>` возвращает routing equipmentId; shareId сохраняется. Latest-wins generation защищает от stale resolution. Native association — Phase E, не C1.
- Нет приложения: страница `/e/<id>` ведёт в Play с `referrer=id=<id>`. Первый Android-запуск читает Install Referrer один раз и кладёт тот же pending open. Пустой/чужой referrer помечается проверенным и карточку не открывает. Ошибка Play не помечает проверку. iOS без стора — проверка сразу закрывается.
- Legacy `?s=<shareId>` сохраняется в App Link, cold start, pending и Install Referrer (`id=…&s=…` или полный URL). Невалидный `s` → `shareId` null, ссылка остаётся валидной. `EquipmentShareLink.canonical` без query; legacy `uri` добавляет `?s=`, registry `uri` содержит shareId в path. В bootstrap передаётся `link.uri`, не `canonical`.
- C2 persistence: `equipment_share_state` v3 объединяет pending, accepted context, overlay, UI-intent и OPENED receipt. Inner open сохраняет v1/v2; старые keys/plain URI мигрируются. Correlation — intentId UUID == clientEventId, не equipmentId. Accepted context читается для matching target, OTP/рендер его не очищают. См. `docs/architecture/public-share-c2.md`. `deferredInstall` использует тот же recovery path, внешние события пока запрещены.
- `firstShareBootstrapRun` — только диагностика: ссылку обработал первый `start()` при ещё непроверенном install referrer. Не «новая установка». Stream-ссылки всегда `false`.
- `ShareOpenRecorder.record` вызывается из единого `onAccepted` ingress после durable completion: GA `share_link_opened`, backend OPENED, для гостя durable first touch. Все три независимы, best-effort, навигация их не ждёт. Registry GA использует share_id без equipment item_id; legacy GA сохраняет прежний контракт. Overlay / `afterAuth` запись не повторяют.
- Первый валидный unauthenticated share open сохраняется в secure storage и выигрывает на 30 дней, переживая restart. `verifyOtp` отправляет его как `attribution`; успешный OTP очищает first touch, неуспешный сохраняет. C2 logout очищает first touch и ревокирует общий privacy epoch до remote logout; старые callbacks/state не должны воскресать. Для нового пользователя shareId проходит через user-bound in-memory `PendingSignUp`, GA sign_up — после identity.
- Overlay read/write/clear на одном provider-instance сериализованы; revision меняется при запросе replacement/clear. Claim не удаляет durable overlay: ack только после наблюдения router target. Restart до ack восстанавливает instruction; accepted attribution остаётся после ack. `consumeAgain` сохраняется. OPENED retries используют стабильный persisted clientEventId и Backend dedup, не exactly-once; GA claim durable до dispatch.
- Экран `/e/:id` — `GuestCreateBookingScreen` с `ProkatAppBar`. Back: `pop` если есть стек, иначе landing (`startupLandingLocation`). Гость заполняет форму, первый тап «Создать заказ» кладёт UI-intent и overlay `afterAuth`, открывает вход. После OTP redirect подкладывает landing, consume пушит карточку один раз; форма из intent. Заказ — только повторный тап.
