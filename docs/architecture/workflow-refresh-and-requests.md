# Workflow: рефреш, заказы и заявки

Контекст для смежных задач (live-списки, сокеты, TTL, resume). Это **решения и модель продукта**, не план реализации.

Короткий контракт кода: `lib/features/workflow/AGENTS.md`.

## 1. Когда HTTP, когда сокет

Пока экран открыт и приложение на переднем плане — актуальность через `workflow:update`.

HTTP оставляем в трёх случаях:

1. **Pull-to-refresh** — страховка, если сокет пропустил событие, а экран не сворачивали.
2. **Вход на экран** — `refreshIfStale()` (TTL 30 с у списков, 5 мин у открытого чата). Это не фоновый таймер: повторный REST только если с последнего fetch прошло ≥ TTL.
3. **Разворот после реального фона** — `paused` / `hidden` / `detached` → `resumed`. `inactive` не трогаем (клавиатура, шторка). Пока свёрнуто, сокет часто отключён, события теряются.

Фоновых `Timer.periodic` по заказам/чатам/заявкам **нет**. OTP-cooldown — не рефреш данных.

Ресинк списков: `WorkflowCacheCoordinator.resyncAfterReconnect()` после reconnect (не на первом connect) и после resume. Загруженные чаты, заказы, заявки. Открытый тред: `ChatMessagesNotifier` сам рефетчит сообщения и `currentChat`.

Не делать: интервальный опрос открытого экрана; рефреш на `inactive`.

## 2. Заявка ≠ заказ

**Заявка (`request`)** — тендер клиента: категория, локация, объём, желаемая цена, дата. Без конкретной единицы техники.

**Заказ (`booking`)** — сделка по конкретной технике с конкретным владельцем: цена, дата, `workStatus`, отзыв.

Цепочка: заявка → офферы → принятие оффера → заказ. Пока жива заявка, торг идёт в **чате**. Как только есть заказ, статус чата берётся из заказа.

Экраны разные: «Мои заявки» / лента заявок владельца vs «Мои заказы». Карточка не «переезжает» из одного списка в другой.

## 3. Жизненный цикл заявки на экране списка

Фактические переходы сущности:

`CREATED` → (первый оффер) `RESPONDED` → (клиент принял оффер) `ACCEPTED`  
либо `CANCELLED` (клиент) / `EXPIRED` (~2 часа без принятия).

`VIEWED` есть в enum и фильтрах, но **статус заявки в VIEWED никто не пишет**. Просмотр у владельца — строка `requestView` (скрыть/отметить у себя), не бейдж у клиента.

Фильтры списков (бэкенд `GET` requests):

| Экран | Статусы |
|---|---|
| Активные | `CREATED`, `DRAFT`, `RESPONDED`, `VIEWED`, **`ACCEPTED`** |
| История | только `CANCELLED` |
| `EXPIRED` | ни активные, ни история — карточка пропадает из обоих |

Лимит «одна активная заявка» считает только `CREATED` / `VIEWED` / `RESPONDED`. После `ACCEPTED` клиент может создать новую; старая **остаётся** в активном списке.

Карточка клиента: бейдж статуса + вложенные офферы (`created` / `viewed`). Это и есть смена вида, пока заявка не стала заказом.

## 4. Что происходит при отклике собственника

Не «сразу в заказы». Оффер:

- заявка → `RESPONDED` («Offers Received»);
- создаётся чат, если его не было;
- оффер появляется под карточкой;
- пуш + `workflow:update` (`OFFER_CREATED`).

Заказа ещё нет.

Когда клиент **принимает** оффер:

- создаётся `booking` `CONFIRMED` → экран заказов и чат;
- заявка → `ACCEPTED`, **остаётся** в активных заявках («Booking Created»);
- остальные офферы → `CLOSED`.

Заявка и заказ какое-то время живут **параллельно**.

Отмена → история, чат в архив. Истечение → заявка исчезает из списков, история не пополняется. Ручного «удалить карточку» нет, только отмена.

Ответ на развилку a/b/c: **b** (живёт и меняет вид, заказ появляется отдельно). Не **a** (отклик ≠ переезд в заказы). Не **c** (отмена и истечение убирают карточку; `ACCEPTED` висит без ручного удаления).

## 5. Live заявок: тот же канал, другая аудитория

**Канал один: `workflow:update`.** Отдельный канал для заявок не нужен: бэкенд уже кладёт `request` / `offers` в тот же payload, что и заказы. Комнаты — участники сделки (`user:{id}`), как у заказов.

**Не делать** широковещательную комнату «всем владельцам». Лента чужих тендеров («Запросы на аренду», будущий таб «Все») — каталог, не сделка. Live такой ленты — другой продукт (discovery), не workflow. Новые заявки по-прежнему: пуш + HTTP. `createRequest` **не** эмитит workflow.

У заказов live на списке оправдан: вторая сторона крутит тот же объект. У заявок:

| Действие | Кто получает `workflow:update` | Что патчится |
|---|---|---|
| Оффер / принятие / отмена при наличии чата | клиент + владельцы-участники | чат, офферы (invalidate), списки заявок участников |
| Отмена без чата («новый запрос» в ленте) | только клиент | список заявок клиента; лента остальных владельцев — следующий HTTP |
| Новая заявка в ленте владельца | никто в workflow | пуш; вход / pull / resume |

Coordinator патчит списки заявок **участников** так же, как заказы: `CANCELLED` / `EXPIRED` → убрать из active; history клиента — патч или `invalidate()`. Лента владельца, если карточка уже в кэше и событие дошло (был чат) — тоже remove. Если чата не было, карточка уйдёт на pull-to-refresh, вход (`refreshIfStale`) или resume-ресинк. Для этого `GET /requests/owner` по умолчанию (и при `status=ACTIVE`) **не отдаёт** `CANCELLED` / `EXPIRED`.

Не ждать, что после принятия карточка «уедет» в заказы.

Смена продукта на **a** («отклик → сразу в заказы») или **c** («висит, пока не удалю») — сначала контракт списков, потом сокеты. Будущие вкладки «Мои отклики» / архив клиента — участники, тот же канал.

## 6. Что уже сделано в клиенте

- Списки чатов: вкладки Active / Archive; в списке `bookingSummary`, полного `booking` нет; подпись тайла из summary.
- `workflow:update` патчит открытый чат, списки чатов, активные/история заказов, списки заявок участников; офферы/торг — invalidate family.
- Resume-ресинк загруженных чатов, заказов, заявок (не только если сокет реально переподключился).
- Дубль HTTP списков чатов из sidebar-bootstrap на resume убран: один ресинк в workflow.

Не трогать: `notification:new`, `chat:message:new`, `chat:sidebar:update`. Админка (`prokatWeb`) канал не слушает.

`AppSocketService.on` **перезаписывает** хендлер — только fan-out сервисы. `ChatSocketNotifier` мёртвый код, не live-путь.

## 7. Известные дыры продукта (не обязательно чинить в том же PR)

- `EXPIRED` нет ни в ACTIVE, ни в HISTORY.
- `RequestStatus.VIEWED` на сущности заявки не выставляется.
- `ACCEPTED` заявка остаётся в активном списке клиента (и в ленте владельца по тому же фильтру) параллельно с заказом.
- Family офферов/торга на resume не инвалидируется целиком; открытый чат подтягивается через `currentChat.refresh()`.
