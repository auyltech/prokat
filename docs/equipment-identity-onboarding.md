# Добавление техники: identity и достоверные характеристики

Living-document направления. Обновлять по мере исследований и решений. Не подменяет roadmap интеллектуального подбора.

Статусы в тексте:

- `CURRENT` — так устроен код сейчас
- `FACT` — сверено с документацией API или исходником зависимости, на нашем устройстве не запускалось
- `MEASURED` — число получено прогоном на нашем коде и данных
- `DECIDED` — решение этого направления
- `PROPOSED` — гипотеза до измерений
- `NOT TESTED` — код или протокол есть, прогона не было
- `FUTURE` — после каталога подтверждённых машин

Дата первого прохода: 2026-10-02. OCR-движки пересмотрены: 2026-10-02, второй проход.

## 1. Product goal

`DECIDED`

Собрать каталог реальной техники с достоверными структурированными характеристиками. Пока владелец вводит модель и ТХ руками, каталог для будущего подбора непригоден: долго, поля пустые, опечатки, одна и та же модель заполнена по-разному, модератор смотрит слишком много.

Порядок приоритетов:

1. Владельцу предельно просто добавить машину.
2. Максимум работы делает система.
3. Человек видит исключения, конфликты и сомнения.
4. Достоверность важнее заполненности.
5. Неизвестная характеристика лучше выдуманной.
6. Не строить тяжёлую anti-fraud/CV-систему без измеренного риска.
7. Автоматизацию можно усиливать слоями, не переписывая модель данных.

Целевой жест владельца: несколько нажатий, фото машины, подтверждение регистрационных данных. Паспортные ТХ руками не переписываются.

Интеллектуальный подбор по задаче — `FUTURE`. Он начинается после этого каталога, не вместо него.

## 2. Current flow

`CURRENT`

Создание черновика, экран `CreateEquipmentScreen`:

1. Группа каталога: техника или оборудование.
2. Категория из каталога владельца.
3. Город. Если пусто, подставляется город профиля.
4. Название, обязательное.
5. Модель, обязательная свободная строка. Справочник моделей не предлагается.
6. Госномер обязателен только для техники. Поле — латиница, цифры и пробелы, не длиннее 12 символов (`sanitizeKzPlate`). Кириллица выбрасывается, а не транслитерируется.
7. `POST /equipment` создаёт строку со статусом `DRAFT`, `isVisible: false`. Пустые `EquipmentSpec` создаются по `CategorySpec` выбранной категории. Ответ без тела карточки, экран просто закрывается.

Дальше карточка владельца:

- Фото: `image_picker` (камера или галерея), кроп 4:3 через `image_cropper`, загрузка на backend. Живого потока кадров нет. Отдельного camera-плагина нет.
- Общие поля (название, город, цены, комментарий) можно менять и после модерации.
- Модель, госномер, характеристики и фото камеры редактируются только в `DRAFT` и `REJECTED`. После одобрения эти блоки только для чтения.
- Отправка на модерацию: `PATCH` статуса в `CREATED`. Нужны фото, категория, название, модель, город, цена > 0, обязательные характеристики. Для техники ещё госномер.
- `CREATED` — карточка только для просмотра.
- `REJECTED` — правка и повторная отправка.
- Админка правит модель, номер, характеристики и статус напрямую. Отдельного контура «профиль модели» у модератора нет.

Характеристики — значения на конкретной единице (`PUT /equipment/:id/spec-values`). Общего проверенного профиля модели, из которого они копируются, нет.

## 3. Target UX

`PROPOSED`

Владелец выбирает категорию (автоопределение категории пока не обещано), фотографирует машину так, чтобы был виден госномер, и наводит камеру на фрагмент документа, где видны номер и модель. Фото документа на backend не уходит и не хранится. На устройстве остаются только извлечённые строки.

Сервер отдельно читает госномер с уже загруженного фото машины и сравнивает его с номером из документа. Совпадение двух независимых наблюдений — основание для черновика, не флаг `verified` с клиента.

Если каталог узнал модель, экран показывает одну карточку «Распознано: КамАЗ 65115» и кнопки «Верно» и «Изменить». Нажатие подтверждает выбор пользователя, не государственный факт. Несколько похожих модификаций показываются списком. Ручной ввод — запасной путь.

Полный техпаспорт, VIN и шильдик не обязательны. eGov — необязательный более доверенный путь, не замена OCR.

## 4. Trust model

`DECIDED` для архитектуры спайка. В продукт не включено.

Слои, которые нельзя схлопывать:

`raw observation` → `normalized observation` → `evidence` → `verification decision`

OCR только наблюдает текст. Он не ставит «машина подтверждена».

Решение `decideVerification`:

| Решение | Когда в спайке |
| --- | --- |
| `retry` | Нет двух согласованных кадров, номер неоднозначен или сработала даже «безопасная» правка символа |
| `insufficientEvidence` | Номер стабилен и без правок, но второго источника (фото машины на сервере) ещё нет. Это не очередь модератора |
| `review` | Номера двух источников разошлись, дубль, конфликт, модель не разрешилась |
| `autoPass` | Стабильный номер документа, тот же нормализованный номер с фото машины, модель разрешилась, нет конфликта и дубля |

`client says verified=true` доказательством не считается.

Позже в те же слои ложатся server OCR фото машины, eGov, VIN, отметка модератора, проверка дублей. Слои `FUTURE`, контракт решения уже разделён в коде спайка.

Предварительная политика `PROPOSED` и может сузиться после измерений на реальных бланках:

- `AUTO_PASS` — только когда документ стабилен, формат номера понятен, server OCR фото машины дал тот же номер, модель разрешилась, конфликтов нет.
- `RETRY` — смаз, блик, нестабильный текст, слишком мелкий кадр, один неоднозначный символ. Пользователь просто переснимает.
- `REVIEW` — расхождение номеров, двусмысленная модель, дубль, конфликт источников новой модели, подозрительный сигнал. Только это идёт человеку.

Anti-fraud сверх этого (live-камера вместо галереи, nonce сессии, Play Integrity / App Attest) — `FUTURE`, после того как будет видно, что простой сверки недостаточно.

## 5. Data ownership: model vs unit

`CURRENT`

| Что есть | Чего нет |
| --- | --- |
| `Equipment.model` — свободная строка на единице | Профиля характеристик модели |
| `EquipmentModel` — id, имя, категория, иконка. При создании единицы не заполняется | Связи «все XE215C делят один профиль» |
| `EquipmentSpec` — значение характеристики этой единицы | Происхождения значения и уровня доверия |
| `Spec` / `CategorySpec` — словарь полей категории: число, строка, да/нет, выбор | Заводского datasheet |
| `Document` может висеть на единице (`EQUIPMENT`, тип в том числе `EQUIPMENT_OWNERSHIP`) и хранит URL файла | Сценария паспорта в мобильном API. VIN/serial в API нет |

`DECIDED`

Уточнение конкретной машины не переписывает профиль модели и не копируется на следующие такие же машины. Пример: у модели параметр X = 10, владелец одной машины утверждает X = 12. Это unit-specific override, не новое значение модели.

`PROPOSED`, в схему не переносить, пока нет спайка характеристик:

- Canonical Model Profile — один раз на модель/модификацию: заводские значения только тех `Spec`, которые уже есть в категории, плюс источник каждого числа.
- Equipment Unit ссылается на профиль и хранит свои отличия отдельно.
- `Equipment.model` как свободная строка для этого недостаточен.
- `EquipmentModel` в текущем виде — только имя и категория, характеристики на него не повесить без новой сущности или расширения.
- `Document` не использовать как хранилище фото паспорта: цель — не хранить снимок. Позже можно хранить текстовое evidence без файла.

`FUTURE` источник ТХ для новой модели, по убыванию доверия: документация производителя, официальный дилер / datasheet, несколько сходящихся технических источников, прочие источники с явным низким доверием, человек при конфликте или дыре. ИИ не додумывает пустые поля и не путает модификации. Поиск в интернете на каждую следующую машину той же модели не повторяется. Цифрам из LLM без сохранённого источника автоматически не доверять.

## 14. Resolver канонической модели

`PROPOSED`. Таблицы и код не создавать, пока этот раздел не принят отдельно. Раздел заменяет прежнюю схему `baseCode` = шасси и числовой код. `modelCode` — строка.

Слои не смешивать:

| Слой | Пример | Что это значит |
| --- | --- | --- |
| Raw OCR | `KAMAZ 65115` | не переписывается |
| Фрагменты | производитель `KAMAZ`, код `65115` | разбор строки |
| Кандидат | `КамАЗ 65115` | гипотеза resolver |
| Привязка единицы | владелец нажал «Верно» | это его машина, не проверка завода |
| `VERIFIED` модель | профиль ТХ принят один раз | только тогда ТХ копируются следующим машинам |

Нажатие «Да, это КамАЗ 65115» не переводит модель в `VERIFIED` и не подтверждает заводские характеристики.

### Как называются реальные машины

`CURRENT`, локальная база, не production. Снимок каталога в приложении короче живого списка категорий.

В `Equipment.model` сейчас свободный текст, не справочник: `КАМАЗ 65115` на вакуумной машине, отдельно `КАМАЗ` и `камаз` на самосвале и вакууме, `Зил-130`, `Газель`, `Supersucker`, `КАМАЗ Длинномеры`, `КМТ-2` и `GMT-2` как разные единицы, плюс мусор вроде `да`. `EquipmentModel` — 0 строк, ни одна единица на него не ссылается.

Категории, которые владелец видит, и как устроена identity:

| Категория | Что отличает машину | Как это уже лежит в данных |
| --- | --- | --- |
| Вакуумные | цистерна, рукав, глубина | в модели часто пишут шасси: `Зил-130`, `КАМАЗ 65115` |
| Самосвалы | кузов, тип разгрузки | в модели бывает только марка: `КАМАЗ` |
| КМУ и автокраны | стрела, грузоподъёмность | отдельное поле `chassis_model`: «Марка и модель шасси» |
| Экскаваторы | ковш, глубина, масса | код целиком, шасси в схеме нет |
| Вилочные | грузоподъёмность, вилы | код целиком, как `42-7FG15` |
| Длинномеры | — | категория попала в строку модели: `КАМАЗ Длинномеры` |

Автовышки, бульдозеры, тракторы, автобусы и буровые в базе есть, но скрыты и без характеристик. Отдельные сущности шасси и надстройки из них не следуют. Подсказка поля модели в приложении — `АВ-10 КамАЗ 65115`: код установки стоит первым, не «шасси, потом вариант».

Поэтому `modelCode` хранит код как строку: `65115`, `42-7FG15`, `XE215C`, `D65PX`, `PC210LC-11`. Дефис внутри кода не разрезает модель. Необязательный `modificationCode` — только второй явный токен, чаще текст в скобках (`КО-505А`). Он не называется шасси и не называется установкой. У кранов шасси остаётся строковой характеристикой `chassis_model`, не таблицей.

Один и тот же код в двух категориях — две модели. `КАМАЗ 65115` уже записан как вакуум. Самосвал с тем же кодом имел бы другие ТХ и не должен получить цистерну.

### Минимальная схема

- `Manufacturer` — каноническое имя. Из OCR сам не создаётся: иначе `GA3` станет маркой.
- `ManufacturerAlias` — точная строка одной марки. Ключ уникален на всю таблицу: NFKC, обрезка, схлопнутые пробелы, единый регистр. Дефисы не выкидывать. `KAMAZ` → `КамАЗ` только если alias заведён. `GA3` alias `ГАЗ` не является. Общей транслитерации нет: в базе `КМТ-2` и `GMT-2` — разные машины.
- `CAT` / `Caterpillar` и `BELARUS` / `МТЗ` в данных проекта не связаны. Сливать их заранее нельзя. Оба alias можно повесить на одну марку только явной записью. На бланке трактора было `BELARUS`, не `МТЗ`.
- `CanonicalEquipmentModel` — `manufacturerId`, `categoryId`, `modelCode`, необязательный `modificationCode`, `displayName`, `status`. `displayName` только для экрана, в ключ не входит.
- Уникальность живой строки: производитель + категория + нормализованный `modelCode` + нормализованный `modificationCode`. `КамАЗ 65115` и `KAMAZ 65115` в одной категории сходятся в одну строку, потому что alias срабатывает до вставки.
- Профиль ТХ — значения `Spec` этой категории плюс источник. Пустое поле не заполняется догадкой.
- На единице остаётся строка `Equipment.model` как подпись. Позже ссылка на каноническую модель. Пометка в схеме «убрать `model`» для identity не выполнять.

`EquipmentModel` не расширять. Это имя, категория и иконка с инициальной миграции. Записей нет. Код создания нет: поле есть в админской проверке формы и в колонке импорта, таблица участвует в запрете смены группы категории, в разборе картинки и в том, чтобы иконку модели не удалили вместе с аккаунтом. Выкидывать таблицу в первой миграции не нужно. Новая сущность рядом дешевле, чем навешивать жизненный цикл на пустой справочник иконок. Удаление старой таблицы — отдельная уборка после того, как эти четыре места перестанут её читать.

### Жизненный цикл модели

Свои статусы, не статусы объявления (`ACCEPTED`) и не статуса владельца (`APPROVED`):

| Статус | Смысл |
| --- | --- |
| `PROPOSED` | имя пришло из OCR, выбора владельца или внешнего поиска. Можно показать как кандидата. ТХ следующим машинам не копировать |
| `VERIFIED` | профиль категории проверен один раз. Только этот статус заполняет ТХ следующей машины |
| `REJECTED` | ошибочное имя, вроде мусора из поля модели |
| `MERGED` | дубль; ссылка на оставшуюся строку, чтобы старые единицы не повисли |

Первая машина создаёт `PROPOSED`, не `VERIFIED`. Черновик объявления сохраняется сразу, владелец не ждёт профиль. Вторая машина с тем же ключом цепляется к той же `PROPOSED` и тоже не получает заводские ТХ. После одной проверки модератором статус становится `VERIFIED`, и следующие проходят короткий путь.

### Resolver известной модели

Без LLM и без выбора «ближайшей строки»:

1. Raw сохранить отдельно.
2. Производитель — точный alias после нормализации.
3. `modelCode` — точное совпадение нормализованной строки. Совпадение одних цифр, как `65115`, только усиливает уже точный код, не заменяет его.
4. Категория должна совпасть. Вакуумный `65115` не предлагать самосвалу.
5. `modificationCode` — точное совпадение, если он есть. Две живые модификации одного кода — список, даже если OCR назвал одну. `АПТ-18` и `АГП-18` автоматически не выбирать.
6. Ровно один `VERIFIED` — карточка «Верно?». Несколько — короткий список. Ноль — поток новой модели. `PROPOSED` можно показать как «ещё не проверена», без копирования ТХ.

### Новая модель

На сервер уходит текст и категория, не фото документа.

Наблюдение → кандидат на экране → «Верно» → строка `PROPOSED` и черновик техники → позже внешний поиск и черновик профиля с источниками → модератор один раз → `VERIFIED`.

Пока статус не `VERIFIED`, владелец может заполнить характеристики своей машины как сейчас. Эти числа остаются на единице.

### Уточнение одной машины

Профиль модели — заводские значения для следующих таких же машин. `EquipmentSpec` — факт этой машины: другая стрела, другой ковш, другое число. Правка единицы профиль не меняет и на соседей не копируется.

Чтобы будущий подбор их не спутал, у значения единицы нужен признак происхождения: скопировано из профиля или уточнено владельцем. Пока признака нет, скопированное и введённое вручную неразличимы. На экране это «значение модели» и отдельно «моё уточнение». Подбор, когда он появится, берёт уточнение единицы, если оно есть, иначе значение профиля.

### С чего начать пустую базу

Сначала марки и alias, без моделей. Плохой OCR вроде отдельного мусорного имени становится `PROPOSED` и не размножает ТХ. Модератор отклоняет его один раз. Хорошее имя проверяется один раз и после `VERIFIED` заполняет следующих. Создание такой строки из наблюдения ещё не сделано: это раздел 15.

## 15. Implemented foundation

`CURRENT` для таблиц и resolver. Остальной раздел 14 — по-прежнему `PROPOSED`, пока не назван здесь как реализованный.

Реализовано в `prokat-backend`, миграция `20261002180000_canonical_equipment_model_registry`:

- `Manufacturer` с каноническим именем и отдельным ключом сравнения.
- `ManufacturerAlias`. Один нормализованный alias принадлежит только одной марке. Совпадение только точное. `GA3` не становится `ГАЗ`.
- `CanonicalEquipmentModel` рядом со старым `EquipmentModel`. Старая таблица не удалена и не заполняется.
- Статусы `PROPOSED`, `VERIFIED`, `REJECTED`, `MERGED`. `MERGED` без цели или на саму себя база не примет.
- Живая уникальность: производитель + категория + код + модификация. Пустая модификация — один слот. `REJECTED` и `MERGED` этот слот не занимают, поэтому дубль можно слить в живую строку, а мусор не блокирует её навсегда.
- `Equipment.canonicalModelId` необязателен. Создание и правка техники его не заполняют. `Equipment.model` остаётся строкой на объявлении.
- Resolver читает справочник и возвращает `uniqueVerifiedCandidate`, `proposedCandidate`, `multipleCandidates`, `noCandidate` или `manufacturerUnknown`. Он ничего не записывает.

Нормализация: юникод NFKC, обрезка, лишние пробелы, нижний регистр. Дефис остаётся. Похожие буквы и алфавиты не склеиваются.

### Привязка единицы к модели

`CURRENT`, backend. Flutter ещё не вызывает эти запросы.

```text
наблюдение (марка, код, модификация?)
↓
POST /equipment/:id/canonical-model/resolve   — только чтение
↓
кандидаты
↓
явное подтверждение владельца
↓
POST /equipment/:id/canonical-model/confirm
  kind: existing  → готовая модель
  kind: proposed  → найти или создать PROPOSED
↓
Equipment.canonicalModelId
```

- Категория берётся из самой техники, клиент её не присылает.
- Ответ resolve: `outcome`, имя марки, список кандидатов с `canonicalModelId`, `displayName`, кодами и статусом. Нормализованные ключи наружу не уходят. `PROPOSED` и `VERIFIED` видны по статусу.
- `existing`: клиент шлёт только id. Сервер перечитывает модель, переходит от `MERGED` к живой строке, отказывает для `REJECTED` и другой категории.
- `proposed`: марка только из существующего alias. Код — один токен без скобок. Подпись строится как «марка код (модификация)». Сырой OCR в подпись не идёт. Модель всегда `PROPOSED`.
- Гонка двух владельцев: база пропускает одну живую строку. Проигравший запрос перечитывает её и привязывает к ней свою машину.
- Повтор того же подтверждения — `alreadyLinked`. Другую связь молча не перезаписывает: нужен `replaceExisting: true`.
- Привязка возможна только в `DRAFT` и `REJECTED`. После отправки на модерацию и после одобрения — `409`.
- `Equipment.model` не меняется: подпись владельца вроде `АВ-10 КамАЗ 65115` несёт код установки, которого в канонической строке может не быть. Приложение по-прежнему показывает её. `EquipmentSpec` не трогается.

Статус привязки проверяется тем же правилом модерируемых полей, что и остальные owner-facing ручки (ниже).

Не реализовано: OCR → API, экран подтверждения во Flutter, наполнение марок и alias и их админка, поиск характеристик, TechnicalProfile, проверка модели до `VERIFIED`, копирование `EquipmentSpec`, признак «уточнение владельца», eGov, экран модератора, сид спорных пар вроде `BELARUS` / `МТЗ`. Тестовые марки живут только в тестах.

Открытый риск: если OCR назвал модификацию, а в справочнике есть только соседняя (`АГП-18` вместо `АПТ-18`), resolve вернёт `noCandidate`, и владелец может подтвердить новую `PROPOSED` с ошибочной модификацией. Она не станет `VERIFIED` без проверки, но очередь получит лишнюю строку.

### Модерируемые поля после отправки

Flutter UI — UX boundary, но не integrity boundary. Backend обязан гарантировать неизменность модерируемых данных после submission.

moderated lock не отменяет будущую поддержку модификаций и Equipment-specific overrides; он только запрещает скрыто менять уже проверенные данные существующими owner-facing endpoints.

Модерируемые поля: `model`, `plateNumber`, `categoryId`, `canonicalModelId`, характеристики (`EquipmentSpec`), фото. Не модерируются: название, цены и тарифы, город, комментарий и условия аренды, онлайн, рабочий статус, бронирования, биллинг.

`CURRENT` до изменения. Приложение запрещало правку регистрации, характеристик и фото вне `DRAFT` / `REJECTED`, категорию после создания не меняло вовсе. Сервер статус не проверял: `PATCH /equipment/:id` (модель, номер, категория), `PATCH /:id/category`, `PUT /:id/spec-values`, загрузка, обложка и удаление фото принимали правку от владельца в любом статусе, включая `CREATED` и одобренную технику. Проверку статуса имела только привязка канонической модели.

`TARGET`. Владелец меняет модерируемые поля только в `DRAFT` и `REJECTED`. В `CREATED`, `ACCEPTED`, `AVAILABLE`, `BOOKED`, `MAINTENANCE`, `DISABLED`, `ARCHIVED` — контролируемый `409`. Немодерируемые поля по-прежнему правятся. Админ правит через те же ручки и lock не получает.

`IMPLEMENTED`, `prokat-backend`, `equipment.moderated-fields.ts`:

- Ошибка `409 CONFLICT:EQUIPMENT:MODERATED_FIELDS:LOCKED`, в `details` статус и список полей.
- `PATCH /equipment/:id` не частичный: приложение каждый раз шлёт модель, номер и категорию вместе с названием. Поэтому считается только реальное изменение. Поля нет или значение то же — правка проходит. Другое значение или очистка заполненного — lock. `null` и пустая строка — одно и то же «пусто». Пустой `categoryId` значит «не менять», как и раньше.
- `PATCH /:id/category` с текущей категорией — ничего не делает и отвечает успехом. Другая категория — lock.
- `PUT /:id/spec-values`, загрузка, обложка и удаление фото — сами по себе изменения, поэтому вне `DRAFT` / `REJECTED` отклоняются. Фото отклоняется ещё до загрузки файла; если статус сменился во время загрузки, файл удаляется из хранилища.
- `canonicalModelId` в схеме `PATCH` нет: поле отбрасывается, записать его можно только через confirm. Confirm использует тот же список статусов, свой код `CANONICAL_MODEL:LOCKED` и действует и для админа.
- Гонка «прочитали `DRAFT` → владелец отправил на модерацию → записали правку» закрыта: перед записью строка техники блокируется (`SELECT … FOR UPDATE`) и статус проверяется заново в той же транзакции.
- Удаление фото: сначала строка в базе, потом файл. Раньше при сбое запись могла остаться без файла.

`FUTURE`. Модификации и уточнения одной машины (unit override) придут отдельными командами со своим статусом и проверкой, а не через снятие lock со старых ручек. Правка одобренных данных владельцем — только через повторную модерацию.

## 6. OCR engines

Общий слой над движком, `DECIDED` для спайка: `OcrObservation` / `OcrFrameResult` в `lib/dev/equipment_identity/ocr_observation.dart`. Дальше тот же парсер. Типы ML Kit и Vision в Dart не протекают.

Один и тот же native engine на обеих платформах не обязателен. Для manufacturer/model ML Kit Latin больше не кандидат в основной OCR. Следующий кандидат — PaddleOCR Cyrillic, он ещё не подключён и baseline не выбран.

### Вариант A — `google_mlkit_text_recognition` 0.17.1 на Android и iOS

`FACT`, пакет в `pubspec.yaml` не добавлен.

- Только Android и iOS, обработка на устройстве.
- Latin по умолчанию. Китайский, деванагари, японский, корейский — отдельные пакеты. Кириллического скрипта нет.
- Android-зависимость плагина: `com.google.mlkit:text-recognition:16.0.1`. Это bundled-модель, не Play Services. Google описывает bundled как доступную сразу после установки и пригодную офлайн; unbundled (`com.google.android.gms:play-services-mlkit-text-recognition:19.0.1`) качается через Play Services и на первом запуске без сети может быть не готова. Прирост размера Google указывает примерно 4 МБ на скрипт на архитектуру для bundled и около 260 КБ для unbundled. Наш APK не взвешивался (`NOT TESTED`).
- iOS плагина: deployment target 15.5, исключение armv7. У проекта в `ios/Podfile` стоит 15.0, и post_install принудительно пишет 15.0 всем pod-таргетам. Подключение плагина без подъёма цели ломает iOS-сборку либо требует этот подъём.
- Файл: `InputImage.fromFilePath`, EXIF учитывается самим ML Kit. Поток кадров возможен через `InputImage` из bytes, в спайке не делается.
- Bounding box есть у линии. `confidence` у линии в API есть и может быть null. Null значит «оценки нет». Порог по confidence не выбираем, пока нет измерений.
- Для PROKAT bundled предпочтительнее unbundled: добавление техники не должно зависеть от докачки модели. Это trade-off размера APK, не решение включать модель в release, пока spike debug-only.

### Вариант B — Android ML Kit + iOS Apple Vision

`FACT` по API, `NOT TESTED` по качеству. Именно этот вариант собран в debug-спайке, без пакета `google_mlkit_text_recognition` и без смены iOS 15.0.

Android, только debug-сборка:

- `debugImplementation("com.google.mlkit:text-recognition:16.0.1")`.
- Release и profile канал отвечают `debug_only` и модель не линкуют.
- Движок: `TextRecognition.getClient(TextRecognizerOptions.DEFAULT_OPTIONS)`, bundled latin.
- Кадр: `InputImage.fromFilePath`. Наружу уходят строки линий, box, confidence, ширина/высота, миллисекунды.
- `FACT`: `:app:compileDebugKotlin` на этой машине собрался с `text-recognition:16.0.1`. Кадр через модель не прогонялся.

iOS, системный Vision, без дополнительного OCR SDK:

- `VNRecognizeTextRequest`, `recognitionLevel = .accurate`, `usesLanguageCorrection = false`.
- `customWords` при выключенной language correction игнорируется. Это прямо сказано в документации Apple. Для номеров и кодов моделей коррекция словарём опасна, поэтому в спайке она выключена. Включать `customWords` имеет смысл только вместе с correction и только после измерений.
- `recognitionLanguages`: `en-US`, плюс `ru-RU`, если `supportedRecognitionLanguages()` его вернёт на конкретном устройстве. Список языков спайк показывает на экране. На iOS 15 публичные перечни accurate-ревизии называют en, fr, it, de, es, pt и китайский, без ru. ru-RU появляется в перечнях iOS 16. Это чужие списки, не наш прогон (`NOT TESTED`).
- Bounding box наблюдения переводится из нормализованного нижнего-левого угла Vision в верхний-левый пиксельный. Совпадение рамки с картинкой на экране `NOT TESTED`.
- Confidence — `topCandidates(1).confidence`, шкала 0…1, если кандидат есть.
- Ориентация: `CGImagePropertyOrientation` из `UIImage.imageOrientation`.
- Кадр обрабатывается на устройстве. Сеть для Vision не требуется.
- Сторонние Flutter-пакеты Vision не подключены. `apple_vision_recognize_text` завязан на свой camera pipeline. `native_text_recognition` 0.0.2 требует iOS 16 и опубликован как unverified. Свой канал короче и не поднимает deployment target.

Live stream обоих движков возможен и в этом проходе не строится. Сначала one-shot по файлу.

### ML Kit Latin — не основной OCR марки и модели

`FACT`, первое натурное наблюдение, не размеченная таблица и не baseline всего OCR. На реальных строках ML Kit Latin не читает кириллицу как кириллицу. Символы, которых нет в его алфавите, превращаются в похожие латинские, и строка выглядит правдоподобно, но это уже другой текст.

Класс ошибки, не полный протокол кадра:

```text
ground: ГАЗ 2705
OCR:    GA3 2705
```

Это не `NORMALIZED_EXACT`. Обратная транслитерация `GA3` → `ГАЗ` запрещена: исходный символ движок уже потерял, постобработка не восстанавливает его как факт.

`DECIDED`: ML Kit Latin не подходит как основной OCR manufacturer/model для PROKAT. Причины: нет native Cyrillic; mixed-script строка может стать ложной латиницей; это риск ложной identity. Из спайка его не удалять. Оставить как возможный узкий движок для госномера, VIN и чистых латинских идентификаторов, если отдельный замер это покажет. Большой dataset ML Kit по маркам и моделям не собирать.

Основной identity OCR обязан нативно читать смесь кириллицы, латиницы и цифр в одной строке. Типичные строки документа, не edge case:

- `АВТОПОГРУЗЧИК TOYOTA 42-7FG15`
- `ГАЗ 2705`
- `КамАЗ 65115`
- `МАЗ 5337`

OCR обязан сохранить строку. Какая часть означает тип техники, производителя и модель — отдельный resolver. Эти этапы не смешивать. Canonical model движок не выдаёт.

Текущий debug-парсер для этого не годится как evidence: `_prepareLine` переводит омоглифы АВЕКМНОРСТХ в латиницу и выбрасывает остальную кириллицу. В метрику идёт raw движка. Parsed на экране подписан «не метрика».

### Кандидат: `cyrillic_PP-OCRv5_mobile_rec`

`MEASURED` на сгенерированных бланках, в Android не встроен. Итог — NO-GO, таблица в разделе 9. Источники весов: Hugging Face `PaddlePaddle/cyrillic_PP-OCRv5_mobile_rec` и `PaddlePaddle/PP-OCRv5_mobile_det`. Лицензия репозитория PaddleOCR — Apache 2.0.

Что подтверждено документами, не нашим прогоном:

- Это recognition-модель, не детектор. В пару к ней нужен отдельный детектор. Для мобильного пайплайна берётся `PP-OCRv5_mobile_det`: в таблице детекции 4.7 МБ, Hmean 79.0 на их китайско-английском наборе. Детектор скрипт строки не читает.
- Recognition: точность 80.27% на их кириллическом наборе, размер inference 7.7 МБ. Официальные GPU/CPU миллисекунды в той же строке таблицы пустые. Телефонные latency, память и прирост APK — `NOT TESTED`.
- Языки модели по документации: русский, казахский и длинный список других кириллических, плюс английский. `eslav_PP-OCRv5_mobile_rec` казахский не перечисляет, для PROKAT он запасной, не первый.
- Словарь содержит цифры, дефис, `A–Z`/`a–z` и кириллицу, включая казахские `Ә Ғ Қ Ң Ө Ұ Ү Һ І`. Пробел добавляется флагом `use_space_char: true`. Алфавит способен записать mixed-script строку. Это не измеренное качество таких строк.
- Обучение: `max_text_length` 25 и вход `3×48×320`. Пример `АВТОПОГРУЗЧИК TOYOTA 42-7FG15` длиннее 25 символов. Удержит ли inference всю строку — `NOT TESTED`.

Официальный Android-пример (`deploy`, ONNX Runtime) — отдельное приложение, не наш APK:

- minSdk примера 26, ONNX Runtime Android 1.21.1, OpenCV 4.5.3.
- Пресеты примера: `PP-OCRv6_small`, `PP-OCRv6_tiny`, `PP-OCRv5_mobile`. Последний — мобильные det+rec общего PP-OCRv5, не `cyrillic_PP-OCRv5_mobile_rec`.
- API примера принимает свои пути det onnx, rec onnx и `inference.yml`. Подмена recognition-модели этим и делается. Совместимость декодера примера именно с кириллическим yml — `NOT TESTED`.
- Наш `minSdk` остаётся 24. Samsung A125F выше API 26, на нём пример по цели SDK запускается. Поднимать minSdk приложения не нужно.
- Готовый ONNX кириллической recognition в релизе Paddle не лежит рядом с пресетом. Официальный артефакт — Paddle inference (`inference.pdiparams` около 8 МБ на Hugging Face). ONNX получается конвертацией по их гайду. Чужие ONNX на Hugging Face — не тот артефакт, в APK их не класть, пока конвертацию не повторили сами.
- ABI, память и размер ONNX Runtime + OpenCV в нашем debug APK не измерялись.

Официальный iOS-пример — SwiftUI, ONNX Runtime, Xcode 16, deployment target iOS 16+. Пресеты те же, без отдельного кириллического. Это прямой конфликт с iOS 15.0. Цель проекта не поднимать. На iPhone кириллический Paddle в этом проходе не собирать.

### Flutter-пакеты PaddleOCR

Наличия пакета недостаточно.

- `flutter_paddle_ocr` на pub.dev: Android через Paddle Lite 2.10, модели PP-OCRv2/v3 slim, minSdk 24, ABI по сути arm64. Сам пакет пишет, что мобильных `.nb` для PP-OCRv5 upstream не публиковал. Для `cyrillic_PP-OCRv5_mobile_rec` он не подходит.
- Ветка community ONNX (`flutter-paddle-ocr` / заявка PP-OCRv5 через `ModelSource.filePaths`) умеет подставить свои onnx и словарь и заявляет ONNX Runtime. Пример качает `PP-OCRv5_mobile_rec`, то есть не кириллическую модель. Совместимость их CTC-декодера с нашим словарём не проверялась. В production и в этот спайк пакет не берём.

Свой небольшой debug-only bridge допустим, когда в нём будут именно det `PP-OCRv5_mobile_det` и rec `cyrillic_PP-OCRv5_mobile_rec` с её словарём. Пока веса не зафиксированы, второй движок в канал не добавлять: неверный словарь напечатает ложную кириллицу и испортит сравнение.

### Apple Vision, только исследование

`FACT` по чужим спискам, наш iPhone `NOT TESTED`.

- iOS 15, accurate: публичные перечни без `ru-RU`.
- iOS 16, accurate, revision 3: в чужом выводе `supportedRecognitionLanguages` есть `ru-RU` и `uk-UA`, плюс корейский, японский и китайский. Казахского в том списке нет.
- Apple разрешает несколько `recognitionLanguages`. Одновременные `ru-RU` и `en-US` на одной строке документа мы не мерили. `automaticallyDetectsLanguage` с iOS 16 Apple сам называет менее надёжным, чем явно заданный язык.
- Спайк уже спрашивает `supportedRecognitionLanguages()` и добавляет `ru-RU` только если устройство его вернуло. Цель iOS 15.0 из-за этого не меняется.
- Смешанное качество Vision на `АВТОПОГРУЗЧИК TOYOTA 42-7FG15` неизвестно. Решение по iOS не принимать без своего iPhone.

### Tesseract, резерв

`PROPOSED` запасной кандидат, не следующий спайк и не baseline. `rus+eng` даёт Unicode локально, порты на Android и iOS существуют, лицензия Tesseract Apache 2.0. Качество на фото документа и latency против Paddle не сравнивались. Подключать после того, как кириллический Paddle либо подтвердит character fidelity, либо провалит её на коротком наборе.

- На eGov видны услуги регистрации обычных транспортных средств (в том числе по VIN и электронному паспорту у дилера). Это не подтверждённый сервис «отдай третьему приложению данные моей спецтехники».
- Электронные паспорта самоходных машин существуют как правовой режим. Доступа PROKAT к этой системе нет.

Почему eGov не может быть единственным путём:

- технику может добавлять не собственник;
- человек может не дать согласие;
- конкретной машины может не быть в нужном реестре;
- часть спецтехники регистрируется в другом контуре, не как легковой автомобиль.

`FUTURE`: eGov — ускоренный доверенный источник identity, OCR документа — полноценный запасной путь.

Открытые вопросы, без которых интеграцию не проектировать:

1. Есть ли у МВД / комитета транспорта сервис чтения регистрационных данных спецтехники для третьей стороны по согласию?
2. Какие поля он реально отдаёт: госномер, марка, модель, год, заводской номер, VIN?
3. Совпадает ли госномер спецтехники с форматом легкового ГРНЗ?
4. Кто подписывает согласие, если в парк технику вносит не собственник?
5. Срок, отзыв согласия, что хранить у нас вместо сырого ответа госоргана.

## 9. Technical spikes and measurements

Спайк не встроен в создание техники. Debug: Помощь → «OCR spike», `/dev/equipment-identity`. В release маршрута нет.

`MEASURED` только парсер строк, Windows, не телефон: `flutter test test/dev/equipment_identity/identity_observation_test.dart`. Это не OCR.

Парсер, `DECIDED` для спайка:

- Вход — `OcrFrameResult`, не голые строки движка.
- Кириллические двойники А В Е К М Н О Р С Т Х помечаются `cyrillic-homoglyph`. Такой номер не считается подтверждённым.
- Шаблон `3+3+2` — классификация одного знакомого формата, не фильтр. Другая смесь букв и цифр длиной 4–12 остаётся кандидатом `unknown` и не подтверждается.
- `O/0`, `I/1`, `S/5`, `B/8` в любом слоте этого шаблона дают `possibleNormalized` и `ambiguous`. Observed не подменяется. Подтверждённым номер не становится.
- VIN с `I`, `O` или `Q` не принимается.
- `autoPass` в тесте только если два чистых одинаковых кадра, второй источник совпал и модель помечена разрешённой.

`NOT TESTED` как размеченная таблица. Есть одно натурное наблюдение: ML Kit Latin подменяет кириллицу похожей латиницей. Baseline не выбран. PaddleOCR в APK нет: официальный пример несёт другой rec-пресет, а пакет с PP-OCRv2/v3 мерить бессмысленно.

Каталог PROKAT смешанный. Кириллические марки — основной критерий, наравне с латиницей. Удачный plate, VIN и `CAT` baseline не подтверждают.

### Протокол короткого сравнения

Устройство: Samsung A125F, debug-сборка. Сеть для снимка не нужна. Фото в git не класть. Заметки — в `dev_samples/equipment_identity/`.

Сравнение ML Kit и Paddle на одном кадре начнётся, когда в спайке появится второй движок с `cyrillic_PP-OCRv5_mobile_rec`. До этого большой набор ML Kit по маркам не снимать. Парсер под ошибки не подкручивать.

Большой benchmark не нужен. Несколько реальных кадров, которые отвечают на один вопрос: сохраняет ли новый движок исходный mixed-script текст заметно лучше ML Kit Latin.

Минимальные классы строк, писать то, что на бланке:

| Класс | Что должно встретиться |
| --- | --- |
| Cyrillic | `ГАЗ 2705`, `КамАЗ …`, `ЗИЛ …` |
| Mixed | `АВТОПОГРУЗЧИК TOYOTA 42-7FG15` и ещё одна строка «кириллица + латинский model code» |
| Latin | `XCMG XE215C`, `CAT 320D` |
| Identifiers | госномер и VIN, отдельно от модели |

Для нескольких одинаковых документов снять полный кадр и crop области строки. Один кадр прогнать обоими движками, raw не смешивать.

Четыре группы, метрики не склеивать в один вердикт `OCR works`:

| Группа | Что на кадре | Примеры класса, не подмена реальных бланков |
| --- | --- | --- |
| A. Latin model | марка и модель латиницей | `XCMG XE215C`, `CAT 320D`, `Komatsu PC210` |
| B. Cyrillic model | марка и модель кириллицей | `ЗИЛ 130`, `КамАЗ 65115`, `МАЗ 5337`, `Урал 4320`, `БелАЗ` |
| C. Mixed | кириллица вместе с латиницей или цифрами | как на документе |
| D. Identifiers | отдельно от модели | госномер, VIN, serial/model code, если он есть |

`DECIDED`: основная метрика — identity extraction, не полная транскрипция бланка. Идеально читать весь техпаспорт не нужно. В таблицу пишется raw как есть. Метку ставит человек по подстроке manufacturer/model, не парсер.

Для manufacturer/model:

- `IDENTITY_EXACT` — марка и код модели в raw совпали с бланком, включая алфавит. Соседние слова типа техники могут быть порчены.
- `IDENTITY_NORMALIZED_EXACT` — только регистр, пробелы, дефисы. `КамАЗ` и `КАМАЗ` сюда входят. `KamAZ` нет.
- `IDENTITY_USABLE_PARTIAL` — уцелела часть, по которой машину ещё можно отличить, но не вся пара. Пример: в raw есть `65115`, марки нет.
- `IDENTITY_WRONG` — идентифицирующая часть подменена. `ГАЗ 2705` → `GA3 2705` сюда.
- `IDENTITY_MISSING` — марки и кода модели в raw нет.

```text
GROUND: АВТОПОГРУЗЧИК TOYOTA 42-7FG15
OCR:    АВТОПОГРУ... TOYOTA 42-7FG15
identity expected: TOYOTA 42-7FG15
→ IDENTITY_EXACT
```

Слово `АВТОПОГРУЗЧИК` здесь тип техники, не manufacturer. Его порча full-line transcription портит, identity — нет.

```text
GROUND: ГАЗ 2705
OCR:    GA3 2705
→ IDENTITY_WRONG
```

`2705` можно отметить как уцелевший фрагмент. Это не делает manufacturer годным. Транслитерацию обратно в `ГАЗ` не делать. Мусор не подменять маркой из справочника.

Полная строка длиннее 25 символов всё равно записывается отдельно: обрезал ли recognition хвост, и спасает ли crop области `TOYOTA 42-7FG15`. Это эксперимент, не вывод из `max_text_length`.

Плохой кадр помечать `detection` или `recognition`. Detection: нужной области нет в рамках. Recognition: область верная, символы нет. Для ключевых строк recognition гонять ещё и на ручном crop строки.

Plate и VIN считать теми же пятью метками, отдельно от модели. `possibleNormalized` парсера в метрику не подставлять: в протокол идёт raw-строка движка.

Для нескольких одних и тех же документов снять полный кадр и crop области номера или модели. Если crop заметно поднимает точность, это аргумент за рамку на фрагмент, а не за чтение всего паспорта.

На каждый прогон сохранить текст, не файл:

```text
device: Samsung A125F
os:
engine:
image source: camera | gallery
framing: full | crop
group: cyrillic | mixed | latin | identifier
ground truth:
raw:
parsed (не метрика):
elapsedMs:
warnings:
```

Пример разделения этапов, не результат прогона:

```text
raw:
АВТОПОГРУЗЧИК TOYOTA 42-7FG15

parsed candidate:
manufacturer = TOYOTA
model = 42-7FG15
equipmentTypeHint = АВТОПОГРУЗЧИК
```

Рамки есть на экране: скриншот экрана спайка достаточен, сам JPEG не коммитить. Предыдущий полный кадр остаётся в журнале экрана после crop.

Парсер под ошибки этого прогона не подкручивать. Сначала список raw failures. Иначе замер смешает движок и наши догадки.

Порог confidence не назначать до таблицы.

Реальные форматы номеров легковых, грузовых, тракторов и самоходных машин — по-прежнему отдельный research. Один regex их не описывает.

## 10. Decisions

- `DECIDED` Подбор по задаче, eGov, ТХ из интернета и production-flow в этот проход не входят.
- `DECIDED` Фото документа не хранить и не слать на backend.
- `DECIDED` OCR не выставляет verified. Сомнительная нормализация не становится подтверждённым номером.
- `DECIDED` Нехватка второго источника — `insufficientEvidence`, не заявка модератору.
- `DECIDED` `google_mlkit_text_recognition` в `pubspec.yaml` не добавлять: он тянет iOS 15.5.
- `DECIDED` iOS deployment target пока остаётся 15.0.
- `DECIDED` Unit override не становится значением модели.
- `DECIDED` ML Kit Latin не основной OCR manufacturer/model. В debug он остаётся для сравнения и как возможный узкий движок plate/VIN/чистой латиницы.
- `DECIDED` Основной identity OCR должен нативно читать mixed Cyrillic + Latin + digits. Постобработка не восстанавливает потерянный алфавит как факт.
- `DECIDED` Кириллическая марка/модель — обязательный критерий. Транслитерация не `EXACT` и не `NORMALIZED_EXACT`.
- `DECIDED` Годность OCR марки и модели считается по identity-полям, не по полной строке бланка. Повреждённый тип техники при целом `TOYOTA 42-7FG15` может быть `IDENTITY_EXACT`. `GA3` вместо `ГАЗ` — `IDENTITY_WRONG`.
- `DECIDED` Четыре проверенных recognizer не дают надёжную буквальную марку. OCR — наблюдение и источник кандидатов, не авторитетная каноническая модель. Универсальный OCR дальше не перебирать и в приложение не встраивать.
- `PROPOSED` Каноническая модель — новая сущность со статусом `PROPOSED` / `VERIFIED` / `REJECTED` / `MERGED`, не расширение пустого `EquipmentModel`. `modelCode` — строка. Нажатие «Верно» привязывает единицу и не проверяет заводские ТХ. ТХ копируются только с `VERIFIED`.
- `PROPOSED` Tesseract `rus+eng` — резерв после прогона Paddle, не вместо него.
- `PROPOSED` iOS Vision с `ru-RU` проверять на своём iPhone. Официальный Paddle iOS 16+ цель 15.0 не поднимает.

## 11. Rejected alternatives

- Хранить полный техпаспорт и распознавать все страницы.
- Облачный OCR документа.
- Поднять iOS до 15.5 только чтобы поставить Flutter-плагин ML Kit до сравнения с Vision.
- Считать `verified=true` с клиента достаточным.
- Тихо заменять `8` на `B` или `O` на `0` и считать номер подтверждённым.
- Копировать ручную поправку одной машины на все машины модели.
- Доверять числу из интернет-поиска LLM без источника и review.
- Брать малоизвестный Flutter-пакет Vision только чтобы не писать канал.
- Считать ML Kit Latin пригодным для марки, если угадан VIN, номер или латинский model code.
- Восстанавливать `GA3` в `ГАЗ` внутри raw OCR или считать такой alias фактом распознавания.
- Считать ближайшую строку по расстоянию редактирования доказанной моделью. `АПТ-18` и `АГП-18` могут быть двумя разными машинами.
- Брать Flutter-пакет Paddle Lite PP-OCRv2/v3 ради простой интеграции.
- Класть в APK чужой ONNX кириллической модели вместо конвертации официального inference.

## 13. Phased implementation plan
