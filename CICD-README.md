# PROKAT — памятка по CI/CD

## 1. Подготовка новой версии

Пример: готовим `1.2.3+19`.

1. Завершаем разработку и тесты в feature-ветках.
2. Объединяем изменения через PR в `dev`.
3. Обновляем `pubspec.yaml`:

   ```yaml
   version: 1.2.3+19
   ```

4. Создаём каталог `releases/1.2.3/` по существующему шаблону.
5. Заполняем `release.json` и три файла «Что нового»:
    - RU — русский;
    - EN — английский;
    - KK — казахский.
6. Проверяем, что manifest содержит правильную версию и `ready: true`.
7. Запускаем тесты и проверяем окончательный состав релиза.

**Важно:** версия сборки в CI/CD берётся из Git-тега. `pubspec.yaml` поддерживаем в актуальном состоянии для локальной разработки и согласованности проекта.

## 2. Как писать «Что нового»

Пишем кратко, только пользовательские изменения.

Пример для `1.2.3`:

**RU:** Добавлены уведомления о новых версиях приложения. Улучшена обработка публичных ссылок на технику и переходов в приложение.

**EN:** Added notifications about new app versions. Improved handling of shared equipment links and opening them in the app.

**KK:** Қолданбаның жаңа нұсқалары туралы хабарландырулар қосылды. Техникаға ортақ сілтемелерді өңдеу және қолданбада ашу жақсартылды.

Не включаем внутренние технические изменения (CI/CD, рефакторинг, тесты), если они не представляют пользы для пользователя.

Файлы должны соответствовать существующему контракту release scripts. Перед тегированием проверяем их парсером.

## 3. Слияние в main

Принятая схема:

`feature → dev → main`

1. Создаём и объединяем PR `feature → dev`.
2. Проверяем актуальность `main` и `dev`.
3. Если истории разошлись после предыдущего squash, сначала проверяем, что уникальные изменения `main` уже учтены в `dev`.
4. Только после подтверждения безопасности при необходимости выполняем на `dev`:

   ```bash
   git fetch origin
   git merge -s ours origin/main -m "chore: sync main into dev"
   git push origin dev
   ```

5. Создаём PR `dev → main`.
6. Проверяем diff и CI.
7. Выполняем **Squash and merge**.
8. Обновляем локальный `main` и фиксируем полный SHA релизного коммита.

**Запрещено создавать release-теги до попадания проверенного кода в main.**

`-s ours` — не обязательный шаг каждого релиза; применяем только после проверки истории.

## 4. Запуск тестовой публикации (RC)

Для версии `1.2.3+19` создаём два тега на одном SHA из `main`.

| Тег | Результат |
|---|---|
| `rc/android/v1.2.3+19` | GitHub Actions → Google Play Internal Testing |
| `rc/ios/v1.2.3+19` | Codemagic → TestFlight Internal Testing |

Создание и отправка тега запускают соответствующий пайплайн.

Пример для Android:

```bash
git tag -a "rc/android/v1.2.3+19" <MAIN_SHA> -m "Android RC 1.2.3+19"
git push origin "rc/android/v1.2.3+19"
```

Для iOS аналогично, используя `rc/ios/v1.2.3+19`.

Рекомендуемый порядок: сначала Android, затем iOS.

Проверяем результат CI, загрузку в магазин, установку с тестового канала и работу приложения на устройстве.

## 5. Production-публикация

Когда версия готова к публичному выпуску, используем production-теги:

| Тег | Назначение |
|---|---|
| `android/v1.2.4+20` | Google Play Production |
| `ios/v1.2.4+20` | Apple App Store |

Перед запуском:

- Код должен находиться в `main`.
- Версия и release notes должны быть окончательно утверждены.
- Сборка должна пройти тестирование.
- Номер сборки должен быть доступен.
- Production credentials и `PRODUCTION_PUBLISHING_ENABLED=true` должны быть отдельно подготовлены и разрешены.

**Важно:** если конкретный AAB/IPA уже загружен в тестовый канал, для Production желательно продвигать этот же артефакт, а не загружать его повторно с тем же build number. Возможность такого promotion необходимо проверить в CI/CD. Не создавать второй upload одного и того же номера вслепую.

Публикация Android и iOS независима. Фактический выход зависит также от проверки и настроек соответствующего магазина.

## 6. Если магазин отказал

| Ситуация | Действия |
|---|---|
| Ошибка CI до загрузки | Исправить причину; повторный запуск допустим, если артефакт ещё не принят магазином |
| Отклонение метаданных | Исправить описание, скриншоты или документы и повторить отправку по правилам магазина |
| Отклонение бинарника | Исправить код, создать новый коммит, проверить следующий доступный build number и создать новый тег |
| Android прошёл, iOS отказал | Android не трогать; исправить и повторить только iOS |
| iOS прошёл, Android отказал | iOS не трогать; исправить и повторить только Android |

**Ключевые правила:**

- Не перемещать и не перезаписывать опубликованные release-теги.
- Не использовать повторно build number, уже занятый магазином.
- Если `+19` был принят магазином, а затем отклонён, исправленная сборка должна получить следующий допустимый номер.
- Android и iOS могут временно иметь разные build numbers.
- При изменениях, затрагивающих обе платформы, оценивать необходимость новой проверки обеих.
- Не включать автоматическую production-публикацию в ответ на отказ одного магазина.
