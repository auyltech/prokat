# OTP Protection

The right production design is: collect a small installation identifier and app-integrity proof from the app; derive IP/location/network information on the backend; then rate-limit across several dimensions. Do not collect precise GPS, IMEI, serial number, MAC address, contacts, or advertising ID for OTP security.

## Information to collect

| Signal | Source | Purpose |
| --- | --- | --- |
| Normalized phone number | App, validated again by backend | Per-number limits, country/prefix policy |
| `installationId` | Random UUID created once and kept in secure storage | Limit one installation using many numbers |
| Platform | App: Android/iOS/web | Risk rules and diagnostics |
| App version/build | App | Block obsolete or known-abusive versions |
| App-integrity token | Firebase App Check, Play Integrity, or App Attest | Prove the request came from a legitimate app instance |
| `challengeId` | Generated by backend | Bind verification attempts to one OTP request |
| Source IP | Backend/reverse proxy | IP/subnet limits and network reputation |
| IP country, ASN, proxy/Tor/cloud-hosting flags | Derived by backend | Risk scoring; never trust client-provided values |
| Destination prefix/country/carrier/line type | Backend lookup | Reject unsupported or suspicious destinations |
| Request time, outcome, provider message ID | Backend | Auditing, conversion metrics, incident response |

Your client payload could be approximately:

```json
{
  "phoneNumber": "+77001234567",
  "installationId": "random-per-install-uuid",
  "platform": "android",
  "appVersion": "1.4.0",
  "buildNumber": "104"
}
```

Put the app-integrity token in a header such as `X-Firebase-AppCheck`, not in the URL. Firebase supports App Check for custom backends and Flutter directly. [Flutter custom-backend documentation](https://firebase.google.com/docs/app-check/flutter/custom-resource), [Flutter setup](https://firebase.google.com/docs/app-check/flutter/default-providers)

Do not use an FCM token as the primary block identifier. It is useful as an additional correlation signal, but registration identifiers can rotate. [Firebase token-management guidance](https://firebase.google.com/docs/cloud-messaging/manage-tokens)

## Location and country

For OTP security:

- Do not request GPS permission.
- Derive approximate IP country/region on the backend.
- Determine the destination country and prefix from the normalized phone number or a phone intelligence service.
- Treat country mismatch—such as a Kazakhstan number being requested from a foreign hosting provider—as a risk signal, not an automatic rejection.
- Note that `+7` is shared by Kazakhstan and Russia, so `+7` alone does not prove Kazakhstan. Validate the actual numbering ranges or use a lookup provider.

Your privacy policy already mentions device identifiers, location, fraud prevention, account protection, and six-month technical-log retention. [privacy_policy_en.md](C:/Users/User/Documents/GitHub/prokat/assets/legal/privacy_policy_en.md:48) Precise location collected for equipment/work addresses should remain separate from authentication telemetry. If you add IP addresses, network reputation, app-integrity results, or installation identifiers, describe their security purpose and retention explicitly in all three policy languages.

## Server-side rate limits

These are reasonable starting points for a moderate-traffic application; measure false positives and adjust them.

| Scope | Suggested initial limit |
| --- | --- |
| Same phone number | 1 send per 60 seconds, 3 per 15 minutes, 5 per 24 hours |
| Same installation | 5 sends/hour, 15/day, no more than 3 distinct numbers/hour |
| Same IP | 20 sends/hour, no more than 5 distinct numbers/hour |
| Datacenter, proxy, Tor, bad-reputation IP | Much stricter limit or require CAPTCHA |
| OTP challenge | Maximum 5 incorrect verification attempts |
| Phone verification attempts | Around 10 failed attempts/hour, with increasing delays |
| Entire application | Daily provider/spend ceiling plus an emergency circuit breaker |

These limits must run atomically in the backend—commonly with Redis—not in Flutter. Return `429 Too Many Requests` and a backend-calculated `Retry-After`.

Use several buckets together. IP-only blocking harms users behind mobile carrier NAT or shared Wi-Fi; phone-only locking lets an attacker deny service to an innocent number. OWASP recommends account-associated throttling while warning that lockouts can themselves become denial-of-service tools. [OWASP Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)

Twilio’s provider-neutral guidance recommends retry buffers, exponential backoff, and roughly one verification request per phone every 30 seconds; it also recommends limits by number, IP, and device identifier. [Verification best practices](https://www.twilio.com/docs/verify/developer-best-practices), [fraud-prevention guidance](https://www.twilio.com/docs/verify/preventing-toll-fraud)

## OTP lifecycle requirements

The backend should:

- Generate the code with a cryptographically secure random generator.
- Expire it after approximately 3–5 minutes.
- Accept it only once.
- Tie it to `challengeId`, normalized phone number, purpose, and installation.
- Store a keyed digest/HMAC rather than plaintext OTP.
- Never put an OTP in logs, analytics, crash reports, or API responses.
- Invalidate the challenge after success or too many failures.
- Either invalidate older codes on resend or resend the same still-valid code.
- Use generic responses so the API does not reveal whether the phone already has an account.

A six-digit OTP has only one million possibilities, so strict verification throttling is essential. NIST requires rate limiting for low-entropy authenticator outputs and single-use acceptance. [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)

## Blocking a device or number

Maintain a backend denylist with records such as:

```text
subject_type: PHONE | INSTALLATION | IP | CIDR | ASN | PHONE_PREFIX | ATTESTATION_KEY
subject_hash/value
reason
created_at
expires_at
created_by
case_id
```

Recommended behavior:

- Phone block: do not send, but return the same generic response as normal to prevent enumeration.
- Installation block: reject or require CAPTCHA/extra verification.
- IP/CIDR block: temporary by default; avoid permanent blocks on residential/mobile networks.
- ASN block: useful for hosting providers during active automated attacks.
- Prefix/country block: useful for sudden OTP-pumping campaigns.
- Always support expiration, manual unblock, allowlisting, and an audit trail.

A random `installationId` is a useful soft identifier but can be reset by reinstalling the app. For stronger evidence:

- Android: Play Integrity validates the genuine app/device, provides recent-device-activity signals, and has a `deviceRecall` capability for previously flagged devices. It should be one signal among several. [Google Play Integrity overview](https://developer.android.com/google/play/integrity/overview)
- Apple: App Attest creates an app-specific hardware-backed key whose assertions are validated by your server. [Apple App Attest](https://developer.apple.com/documentation/DeviceCheck/establishing-your-app-s-integrity)

Because your project already uses Firebase, Firebase App Check is probably the lowest-friction first implementation: Play Integrity on Android and App Attest with DeviceCheck fallback on Apple.

## CAPTCHA and risk scoring

Do not show CAPTCHA to every normal user. Require it when, for example:

- The installation has requested multiple distinct numbers.
- The IP has exceeded a soft threshold.
- Requests originate from hosting/proxy/Tor networks.
- App attestation is missing or invalid.
- Traffic patterns look automated.
- A phone prefix suddenly has high volume and low completion.

CAPTCHA is defense-in-depth, not proof of legitimacy; OWASP recommends using it adaptively after suspicious attempts rather than necessarily from the first request.

## Monitoring you should not omit

Track and alert on:

- OTP requested, provider accepted, delivered if available, verified, expired, and blocked.
- Verification conversion: `successful verifications / OTPs sent`.
- Send volume and provider cost by country, prefix, ASN, IP, and installation.
- Distinct phone numbers per installation/IP.
- Failed OTP guesses per challenge and number.
- App-integrity pass/fail/missing rates.
- Provider queue depth and error rates.
- Block rates, CAPTCHA rates, and customer complaints/false positives.
- Sudden drops in conversion or spikes in new prefixes.

Your current GREEN API infrastructure limit is not an anti-abuse control: its documented `sendMessage` rate limit is 50 requests per second per instance, which is still enough for major spam and is not scoped to victims, devices, or IPs. [GREEN API rate limiter](https://green-api.com/en/docs/api/ratelimiter/)

## Recommended implementation order

1. Backend rate limits on phone, installation, IP, distinct destinations, and verification attempts.
2. Backend `challengeId`, single-use OTP, keyed storage, generic responses, and `Retry-After`.
3. Global daily send/cost budget with alerts and an emergency kill switch.
4. Random per-installation UUID sent from Flutter.
5. Firebase App Check on both OTP endpoints, initially monitoring before enforcement.
6. Risk-triggered CAPTCHA and IP/network intelligence.
7. Admin denylist/unblock interface with reasons, expiry, and audit logs.
8. For owner accounts and sensitive actions—changing phone, payouts, account recovery—add passkeys or another step-up factor. Phone/WhatsApp OTP proves control of that channel at that moment; it should not be the only protection for high-value account changes.
